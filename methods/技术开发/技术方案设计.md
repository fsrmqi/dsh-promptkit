# 技术方案设计

有一个需求要落地的时候，最贵的不是写码，而是"没想清楚就开干"。

这个 Prompt 会把一次技术方案从"一个想法"推到"能评审、能排期、能验收"的状态。

## Prompt

```
我要做一个技术方案，需求是这个：【写清目标、现状、约束条件】。

请按下面顺序产出一份可以直接评审的技术方案：

1. 目标与边界——我到底要解决什么；明确"本期不做"的事；
2. 现状与约束——现有系统/技术栈/依赖、上线窗口、可用资源；
3. 模块与职责——拆成哪几个模块，各自职责、相互依赖方向；
4. 关键设计——数据模型 / 接口 / 状态机 / 并发与一致性，每个决策给理由；
5. 风险与备选——每个关键决策列出备选方案、放弃它们的原因、剩余风险；
6. 实施步骤——按依赖排序的增量步骤，每一步可验证的结果是什么。

规则：
- 已有确定性信息与"需要验证的假设"分开标注；不确定的写【待确认：…】，不要自行假设；
- 关键决策必须给"为什么选它、不选什么、什么时候它失效"；
- 最后单独给"最值得先验证的 3 个点"，不要塞进正文。
```

## 适用场景

需求评审前、架构设计、重构前对现状做一遍完整梳理，或给别人讲清楚"打算怎么干"。

## 要点

- 六个板块：目标边界 → 现状约束 → 模块拆分 → 关键设计 → 验证备选 → 增量步骤
- 关键决策三件套：为什么选它 / 备选是什么 / 什么条件下它失效
- 明确"本期不做"，比列要做的事更能防范围蔓延
- 未知项标注【待确认】，输出末尾单独给"最该先验证的 3 点"
