# 需求分析

"听懂"需求只是第一步——多数需求承接失败，卡在**口头意思是明确了，但没人把它写成可评审、可分工的规格**。这张卡负责把需求翻译成工程上能评、能排期、能验收的规格摘要。

## Prompt

```
下面这条需求我已经基本理解了：【粘贴原始需求，以及已有需求理解档案/澄清记录（如有）】。

请完成一次需求分析，输出一份《规格摘要》。要求：所有判断区分「已确认事实」与「我的推断」，推断一律标注【推断：…】；不要编造。缺失信息按下方「信息获取优先级」规则处理：先自查，自查不到才追问或标注。

1. 功能点清单——把需求拆成相互独立、可单独验收的功能点，每项包含：名称 / 一句话描述 / 触发场景 / 明确产出；
2. 边界条件——每个功能点的正常流程、边界值、无输入/非法输入/重复触发时的行为；
3. 业务规则——把隐含在被忽视话里的规则显式化（例如定价、权限、时限、状态流转），按「若…则…否则…」描述；
4. 非功能需求——性能、安全、合规、兼容、可用性等约束，没有就明确写"暂无，需确认"；
5. 信息获取优先级（关键）——对每个缺失信息，按顺序处理：① 先自行查证（读代码、查文档、跑命令、搜记录），把查到的写进规格并注明来源；② 确实查不到的，列出**一次性的信息索取清单**（问题集中、每条说明为什么需要、缺了会阻塞什么），一次性向需求方追问；③ 只有当需求方明确回答不了、且该信息不影响主干结论时，才标【待确认：…】继续推进。禁止把本可自行查到的信息标成【待确认】；
6. 冲突与取舍——功能点之间或不同角色之间的冲突，标注冲突点、受影响的决策、可选的取舍方案；
7. 优先级——用 MoSCoW 法（Must/Should/Could/Won't）给每个功能点定级并说明理由；
8. 待确认项清单——只列第 5 条流程后仍悬而未决的决策点，按影响范围从大到小排序；若清单为空，明确写"无待确认项"。

规则：
- 只做规格化，不写技术实现方案；
- 区分"用户事实"与"我方推断"；
- 一条需求若有多个合理解读，列为两种然后让需求方拍板，而不是自己取一个；
- 能自己查到的信息不算"待确认"——先查证、再集中追问、最后才标注搁置；
- 追问必须一次性集中提出，禁止挤牙膏式逐条反问。
```

## 适用场景

需求已基本说清、需要进入排期前；拿到一堆口头或零散需求要整理成正式文档；跨团队交付前把口径统一。

## 要点

- 输出：功能点清单（可独立验收）+ 异常与边界 + 显式化业务规则 + MoSCoW 优先级
- 推断必须标注【推断】，绝不脑补
- 信息获取三级流程：先自查 → 再一次性集中追问 → 最后才标【待确认】；自查到位的不要追问，追问过的不要标待确认
- 追问是索取清单不是反问轰炸：每条说清「要什么、为什么、缺了阻塞什么」
- 多个合理解读时并列呈现、不擅自统一，让需求方拍板
- 只做规格化，不替开发写实现方案
