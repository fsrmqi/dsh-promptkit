# 需求拆解

"这个需求我做完了"和"这个需求真的做完了"之间的差距，几乎都是验收标准缺失造成的。这张卡把需求拆成**每一块都能单独开工、单独验收**的用户故事，并给出最小可交付切片，避免一次性憋大招。

## Prompt

```
请把下面这条需求拆解成可开工的用户故事：【粘贴需求描述，或已写好的规格/需求理解档案】。

拆解结果要求如下：

1. 用户故事集——以「作为一个【角色】，我希望【功能】，以便【价值】」的格式输出，每个故事只包含一个可独立交付的价值点；价值相同只留一个，不重复拆分；
2. 验收标准——每个故事配 2~4 条 Given / When / Then，额外描述该功能的：正常路径、边界值、异常输入、重复触发；
3. 优先级切片——按依赖关系与价值给故事排序，标出：最先交付的最小切片（能形成最小闭环的一组故事）、后续增量；
4. 依赖清单——故事之间谁阻塞谁，用「A 依赖 B」列出；
5. 过细提醒——如果某个故事在拆分中失去独立价值，或拆出来的子项无法单独验收，指出并建议合并。

规则：
- 验收标准必须可以被测试用例直接翻译，避免"系统正常工作"这类不可验收的表述；
- 优先考虑真实用户的角色，而不是内部模块；
- 只拆解，不做技术方案设计。
```

## 适用场景

需求过大无法排期；团队交付后反复返工（尤其验收标准缺失）；需要向开发/测试交接的拆解清单；做 MVP 切片时。

## 要点

- 故事格式：「作为…我希望…以便…」，一个故事一个独立价值
- 验收标准用 Given/When/Then，必须可翻译成测试用例，覆盖正常/边界/异常/重复
- 输出依赖关系 + 最小闭环切片，保证第一刀就能交付可感知价值
- 拆分原则：拆到「有价值、可验收、可单独排期」为止，拆不动就合并
