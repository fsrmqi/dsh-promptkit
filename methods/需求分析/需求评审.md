# 需求评审

高质量需求和普通需求的差别，往往不是在"好不好"，而是在**落到开发手里能不能不带歧义地开工**。这张卡像一次需求走查，专门找出会返工的问题点，并在开工前就给出结论。

## Prompt

```
请评审下面这条需求的可开工度：【粘贴需求描述/用户故事/规格摘要】。

请按五个维度评审，每个维度给出：评分（0-5，5=没有问题）、问题清单、修改建议：

1. 完整性——是否有缺失的角色、场景或异常分支？是否有"大家都懂但没写出来"的默认前提？
2. 无歧义性——同一概念是否被多种叫法/多种理解？数值、时间、许可、状态流转是否有明确口径？
3. 可测试性——每一条能否直接翻译成测试用例？是否存在"系统正常""体验良好"这类永远测不过的验收表述？
4. 一致性——各功能点、各角色目标之间是否有冲突或互相推翻？与既有规则/系统是否一致？
5. 优先级与范围——是否范围蔓延（Won't 混入 Must）？有没有未定义的优先级，或需要裁剪/合并的项？

最后输出评审结论：
1. 问题清单（按 严重 / 中等 / 轻微 分档，每项附：位置、为什么是问题、建议修改）；
2. 最可能引发返工的前 3 个问题；
3. 明确结论：这条需求是否已达到"可开始开发"，若未达到，列出必须先补的【待确认：…】项。

规则：
- 只评审需求文本本身，不臆测开发实现；
- 每一条结论都要引述原文或原文缺失，便于对照；
- 查不出来就写"未见明显问题"，不要凑数式提意见。
```

## 适用场景

需求进入开发前、或快要返工时最后一道闸门；对已写好的规格/用户故事做质量门禁；正式评审前的预走查。

## 要点

- 五维走查：完整性 / 无歧义性 / 可测试性 / 一致性 / 范围控制
- 每条问题都要引述原文，明确"为什么是问题"再给修改建议
- 结论必须给出是否达到"可开工"门槛，卡住的门禁问题列【待确认】
- 查不出来就如实说"未见明显问题"，不凑数
